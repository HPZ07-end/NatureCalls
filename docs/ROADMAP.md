| Stage 3 — Assembly Boundaries（再后续） | 按需要拆分 Player、Facility 等程序集，用 `.asmdef` 管理静态依赖 | 无循环依赖，编译与测试范围合理 |

业务推进以人类批准的最小任务为单位，可与后续技术阶段按实际需求协调，不要求先拆完程序集才实现玩法：

1. M1 Playground（当前）：第一人称移动、姿态驱动第三人称、厕所占位环境、本地 NGO 验证；补齐 Cloud/Relay 和 Windows 验收后集成。
2. 基础 Gameplay 闭环：先澄清相关子树的未定规则，再逐项实现与验证；不在 M1 提前实现。
3. Map 初始化与配置：使用 Unity API 管理场景及每局配置，保留可复现的测试场景。
4. Network：已采用 NGO + MPS/Relay；完成真实 LAN/Relay 跨设备验证及连接失败回归，再按批准需求扩展，暂不做完整大厅或 Host 迁移。专用服务器与其他拓扑的评估见 [ARCHITECTURE](ARCHITECTURE.md)「网络拓扑与专用服务器方案」，2026-11-07 已获用户授权实施 UDP 专用服务器与领队规则。课程服务器目前常驻一个房间 `49.233.132.244:8000`；按需建房见下方待办。
5. 跨平台：Mac/Windows 在同一 Commit 验证导入、规则、场景与构建；LAN 用实际 Host/Client 组合记录。
6. 发布：在截止日前留出团队联调、回归、课程材料整理时间。通过验收的版本经 PR 进入 main，Tag 与 Player Settings 版本一致，产物另行分发。

## 待办：一层（Map2）装置与如厕体验（2026-11-25 团队分工，语义已批准）

语义见 [GLOSSARY](../GLOSSARY.md) 中标注 2026-11-24、2026-11-25 批准的条目。E 准星交互、F 手持操作和通用设施状态表已在 PR #32 完成。

**分工（团队 2026-11-25 确认）**：用户负责一层装置和如厕体验；队友负责拖把等清洁装置、维修与水阀、负一层、一层的拖把与水管、角色类别与参数（CharacterProfile 的数值）、进出游戏界面。

用户这一侧要实现的对象与交互（代码交给 Codex，可视化与 HUD 由 Claude 做）：

| 对象 | 交互与状态 | 依赖与边界 |
| --- | --- | --- |
| `Pipe` 堵塞状态 | 每台用水装置（马桶、小便池、洗手台）属于一条管路；丢纸量与大便量累积堵塞值，到阈值后堵塞；堵塞时冲水或随机触发倒灌；状态在玩家间共享 | 只提供堵塞值、堵塞与倒灌事件和「疏通后重置」入口；维修步骤、水闸和疏通器由队友接入 |
| `Toilet` | 准星 E 冲水；盲拉（无目标圈，以用力瞬间臀部投影判定落进马桶、弄脏马桶或掉到地上）；蹲着小幅挪动；溅水到屁股事件；倒灌后需清洁才能使用 | 挪动受地面状态影响接入 Slipping 时再做 |
| `Urinal` | 镜头正对小便池；鼠标瞄准，尿流按抛物线轨迹；按落点和入射角结算：池内无后果、打在池壁反弹溅到地面（积水）或自己（恶心值）、完全偏离留积水；只做男性站立小便；堵塞时可能倒灌 | 瞄准稳定度以后从 CharacterProfile 读取 |
| `Sink` | 准星 E 洗手（清除手脏）；准星 E 接水（需要手持水桶）；堵塞时可能倒灌 | 水桶属于清洁装置，由队友实现；先留接水接口 |
| `PaperRoll` | 纸量耐久：每次 F 擦拭按本次大便情况消耗不同纸量；纸不够时这卷用完、仍未擦拭（暂定） | 替代固定 3 次 |
| `CharacterProfile` | 运行时角色参数对象，先只有默认值，各系统从它读取速度、急迫值增长、瞄准稳定度、可触及高度 | 类别和数值由队友确定 |
| 可视化 | 尿流、粪便、溅水、脏马桶、倒灌的占位表现，允许夸张 | 正式美术以后替换 |

建议顺序：① `Pipe` 堵塞与倒灌、马桶冲水、洗手台洗手、卷纸纸量、`CharacterProfile` 骨架（规则清楚，可先做）；② 小便池新瞄准与反弹、大便盲拉、溅水反馈（需要手感迭代）；③ 可视化与 HUD；④ Map3 后室接入（方式待定）。

**待定**：堵塞增量与阈值、倒灌概率、各情况用纸量、溅水是否加恶心值、用手擦未洗手的后果、洗手台倒灌后果、干净值影响。急迫值重做与一局的推进方式（不再是定时或固定次数）一起讨论，讨论记录见 [机制讨论](design/mechanics-brainstorm.md)。每步合入后重新部署课程服务器（`scripts/deploy_server.py`），客户端与服务器版本需一致。

## 待办：镇定值扣光后的惩罚不只呕吐（2026-11-26 用户提出，未设计）

用户 2026-11-26 试玩后提出：镇定值（Composure）扣光后吐不应该是唯一的惩罚。现状是归零后进入呕吐倒计时、倒计时内急迫值冻结、只能开关门和冲水，然后呕吐并留下呕吐物（见 GLOSSARY `Composure`、`Vomiting`）。

待讨论：可选的其他后果（例如短时视野或操作受限、拖慢清理、影响他人镇定值的范围加大等）、是否按情境或随机选择、与呕吐的关系（替代还是叠加）、对捣蛋者是否不同。须先作为 Proposed Change 讨论并经用户批准写入 GLOSSARY，再实现。

## 专用服务器按需建房（2026-11-19 记录；2026-11-25 起已实现，见 DEVELOPMENT_STATUS）

> 以下为当时的方案记录。实际实现：broker 监听 TCP 8100，动态房间 UDP 8001–8099，远程隔间创建房间即创建服务器房间，加入时水面列出现存房间；8000 常驻房间保留。

现状：课程服务器上常驻一个房间（`naturecalls@8000`），地址即房间号，所有人进同一个房间，同时只能有一组玩家。

目标：有玩家要玩时才建房，每次给一个新的短房间号，没人后自动回收。

方案（待实施，规则部分需人类批准）：
1. 服务器上常驻一个 Python 房间分配器，经已开放的 TCP 8080 接收请求；建房时在 UDP 8001–8100 中找空闲端口启动一个游戏服务器进程，生成短房间号并记录「房间号 → 端口」。
2. 加入时输入房间号，客户端先向分配器查询端口再连接，玩家不需要知道 IP 和端口。
3. 房间空置一段时间（如 2 分钟）后结束进程并回收端口与房间号；按服务器资源（2 核、3.6 GB）限制同时房间数（约 3 个），满员时提示改用 Relay。
4. 分配器需要防滥用：每个 IP 的建房频率与房间总数上限。
5. 部署：分配器与其 systemd 服务纳入 `scripts/deploy_server.py`。

需要人类决定：大厅是新增「创建服务器房间」入口、把「创建房间」改为先选 Relay 或服务器，还是默认使用服务器建房（属于 GLOSSARY 中 Lobby 定义的变化）；常驻的 8000 房间是否保留为公共房间。分工：分配器、服务器与客户端逻辑交给 Codex，大厅界面由 Claude 实现。
